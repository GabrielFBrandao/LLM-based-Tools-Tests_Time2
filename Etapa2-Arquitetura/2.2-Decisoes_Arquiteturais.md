# Etapa 2 — Decisões Arquiteturais (ADRs Resumidos)

Este documento consolida as decisões arquiteturais críticas, com contexto, decisão, alternativas consideradas e consequências.

---

ADR-001 — Estilo Arquitetural: Monólito Modular com Princípios Hexagonais
- Contexto: Escopo de um único hotel, complexidade moderada, metas de até ~100 usuários concorrentes, necessidade de rapidez de entrega e baixo custo operacional.
- Decisão: Adotar monólito modular em camadas (Apresentação, Aplicação, Domínio, Infraestrutura) com portas/adapters (hexagonal).
- Alternativas:
  - Microserviços: maior isolamento e escalabilidade independente, porém aumento substancial de complexidade operacional (rede, observabilidade, CI/CD, consistência distribuída) e overhead prematuro.
  - Modular monolith sem hexagonal: mais simples, mas com risco maior de acoplamento entre camadas e menor testabilidade.
- Consequências:
  - Positivas: baixa latência intra-processo, transações simples, código testável, caminho claro para extração futura de serviços.
  - Negativas: um único artefato pode crescer e exigir disciplina para manter limites; deploy único impacta todo o sistema.

ADR-002 — Backend: Plataforma e Framework
- Contexto: Necessidade de produtividade, padrão de mercado, suporte a REST, validações, injeção de dependência, testes e migrações.
- Decisão: Adotar Node.js com NestJS (ou alternativa Java Spring Boot caso equipe seja majoritariamente Java). Preferência inicial: NestJS pelo ecossistema JS/TS e integração com SPA.
- Alternativas: Spring Boot (Java), .NET (C#), Django/FastAPI (Python).
- Consequências:
  - Positivas: TypeScript, DI, módulos, pipes de validação, integração com TypeORM, rapidez de prototipação.
  - Negativas: Overhead de Node single-thread para CPU-bound (mitigado por clusterização e natureza IO-bound do app).

ADR-003 — Frontend: SPA com Framework de Componentes
- Contexto: UI moderna, responsiva e acessível; paleta verde/azul; necessidade de componentes prontos (chips, selects, ícones) e produtividade.
- Decisão: SPA com React + Material UI (ou Angular + Angular Material). Preferência: React + MUI.
- Alternativas: Vue + Vuetify, Svelte + SvelteKit + libs.
- Consequências:
  - Positivas: rápido desenvolvimento, comunidade grande, componentes acessíveis e responsivos.
  - Negativas: bundle size e atenção a performance; necessidade de SSR não mandatória no escopo atual.

ADR-004 — Persistência: Banco Relacional (PostgreSQL) + ORM
- Contexto: Entidades com relações claras (Quarto, Hóspede, Reserva), integridade referencial e transações para consistência (RNF-04).
- Decisão: PostgreSQL com TypeORM (ou JPA/Hibernate se Java).
- Alternativas: NoSQL (MongoDB) — melhor para logs/eventos, não ideal para reservas transacionais.
- Consequências:
  - Positivas: transações ACID, migrações, índices eficientes (numero, cpf), queries ricas.
  - Negativas: esquemas rígidos requerem gestão de migrações; tuning de performance quando volume crescer.

ADR-005 — Autenticação e Autorização: JWT + RBAC
- Contexto: Perfis Admin, Atendente, Manutenção; aplicação SPA; necessidade de controle na borda e rotas protegidas.
- Decisão: JWT stateless com roles (RBAC) aplicado nos controladores; refresh token opcional.
- Alternativas: Sessões de servidor com sticky sessions; OAuth2/OpenID Connect (pode ser evoluído no futuro).
- Consequências:
  - Positivas: simplicidade para escalar horizontalmente, fácil integração com SPA.
  - Negativas: rotação/expiração de tokens deve ser bem gerida; proteção contra XSS/CSRF.

ADR-006 — Observabilidade: Logs Estruturados e Métricas
- Contexto: Auditoria mínima (RF-15), diagnósticos, RNF-07.
- Decisão: Logs JSON estruturados com correlação (requestId), níveis (info/warn/error), e métricas básicas (tempo de resposta, contagem de erros) expostas em /metrics.
- Alternativas: Tracing distribuído (OpenTelemetry) — opcional inicialmente.
- Consequências:
  - Positivas: suporte a auditoria e troubleshooting; fácil integração com ELK/Prometheus.
  - Negativas: custo de armazenamento/log shipping; atenção a dados pessoais (LGPD).

ADR-007 — Segurança Aplicacional
- Contexto: RNF-03 (XSS, CSRF, SQLi), LGPD (RNF-10).
- Decisão: Validações server-side, parametrização de queries via ORM, CSP no frontend, sanitização de entradas, CSRF tokens quando necessário, uso de HTTPS, hashing de senhas (bcrypt/argon2), secret management seguro.
- Alternativas: Delegar a WAF e camada externa — não substitui proteções no app.
- Consequências:
  - Positivas: redução de superfícies de ataque e conformidade.
  - Negativas: aumento de complexidade operacional (rotação de segredos, política de senhas).

ADR-008 — Estrutura de Módulos Internos (Bounded Contexts)
- Contexto: Domínio com áreas claras: Quartos, Hóspedes, Reservas, Identidade.
- Decisão: Organizar por módulos/domínios com camadas internas (app/domain/infra) e contratos explícitos entre módulos.
- Alternativas: Organização por camadas cross-cutting (controllers/, services/, repos/ unificados) — tende a acoplamento e God services.
- Consequências:
  - Positivas: coesão por domínio, facilidade de extração futura, maior clareza de ownership.
  - Negativas: disciplina para evitar dependências cíclicas.

ADR-009 — Exportação CSV e Soft Delete
- Contexto: RF-21 (exportar), RF-16 (exclusão lógica) e auditoria.
- Decisão: Implementar exportação via endpoint que respeita filtros ativos; adotar coluna ativo (boolean) e filtros padrão para suprimir entidades inativas.
- Alternativas: Exclusão física — risco de perda de histórico; exportação client-only — inconsistências com filtros server-side.
- Consequências:
  - Positivas: preserva integridade/histórico; exportação consistente.
  - Negativas: necessidade de manutenção de índices considerando ativo=true.

ADR-010 — Estratégia de Evolução
- Contexto: Possível crescimento de demanda e funcionalidades (datas de reserva, pagamentos, relatórios).
- Decisão: Manter limites de contexto e contratos estáveis; considerar extração do contexto de Reservas como primeiro candidato a serviço separado se necessário; adotar feature toggles para evoluções.
- Alternativas: Big bang para microserviços.
- Consequências:
  - Positivas: evolução incremental com risco controlado.
  - Negativas: complexidade progressiva de observabilidade e versionamento de contratos conforme escalar.
