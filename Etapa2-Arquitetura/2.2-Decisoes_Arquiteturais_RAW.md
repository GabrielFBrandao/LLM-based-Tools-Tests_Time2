        <div class="adr-subsection">
          <div class="adr-subsection-title">Contexto</div>
          <p>O sistema possui módulos inter-relacionados onde transações cruzadas são frequentes. Ao criar uma reserva, é necessário verificar e atualizar o status do quarto atomicamente. A equipe é pequena e o time-to-market é relevante. O escopo é limitado a um único hotel.</p>
        </div>
        <div class="adr-subsection">
          <div class="adr-subsection-title">Alternativas Consideradas</div>
          <table class="opt-table">
            <thead><tr><th>Opção</th><th>Vantagens</th><th>Desvantagens</th><th>Adequação</th></tr></thead>
            <tbody>
              <tr class="chosen"><td>✅ Monolito Modular</td><td>ACID nativo, simplicidade, baixo custo, deploy único, chamadas em memória</td><td>Escala como unidade única; disciplina para evitar acoplamento</td><td>Alta — contexto limitado</td></tr>
              <tr><td>Microserviços</td><td>Escala independente, resiliência por serviço</td><td>Alta complexidade, transações distribuídas, custo elevado, over-engineering</td><td>Baixa — complexidade desnecessária</td></tr>

          <p>Adotar <strong>Monolito Modular em 4 Camadas</strong>: Apresentação → Aplicação (API) → Serviços/Domínio → Persistência, com módulos independentes por contexto de negócio (Quartos, Hóspedes, Reservas) dentro de um único processo deployável.</p>

  <!-- S8 — ADR-007 -->
  <div class="section" id="s8">
    <div class="section-header"><div class="section-num">8</div><div class="section-title">ADR-007 — Gestão de Transações e Consistência de Dados</div></div>
    <div class="adr-card">
      <div class="adr-card-header">
        <span class="adr-id">ADR-007</span>
        <span class="adr-card-title">Uso de transações ACID para operações que afetam múltiplas entidades simultaneamente</span>
      </div>
      <div class="adr-card-body">
        <div class="adr-meta-row">
          <span class="adr-meta-chip chip-status-accepted">✔ Status: Aceito</span>
          <span class="adr-meta-chip chip-prio-critical">⚑ Prioridade: Crítica</span>
        </div>
        <div class="adr-subsection">
          <div class="adr-subsection-title">Contexto</div>
          <p>Operações como "criar reserva" e "cancelar reserva" envolvem alterações em múltiplas tabelas. Se parte da operação falhar, o sistema pode ficar em estado inconsistente (reserva criada sem status atualizado, ou quarto liberado sem reserva cancelada). Transações ACID eliminam esse risco.</p>
        </div>
        <div class="adr-subsection">
          <div class="adr-subsection-title">Implementação de Transação Crítica</div>
          <div class="code-block"><span class="cm">// Criar reserva — transação atômica (Prisma $transaction)</span>
async criarReserva(dto: CreateReservaDto): Promise&lt;Reserva&gt; {
  return await this.prisma.$transaction(async (tx) =&gt; {

    <span class="cm">// 1. Verificar disponibilidade dentro da transação (evita race condition)</span>
    const quarto = await tx.quarto.findUnique({ where: { id: dto.quartoId } });
    if (quarto?.status !== <span class="cs">'LIVRE'</span>) {
      throw new ConflictException(<span class="cs">'Quarto indisponível'</span>);
    }

    <span class="cm">// 2. Criar a reserva</span>
    const reserva = await tx.reserva.create({ data: dto });

    <span class="cm">// 3. Atualizar status do quarto para OCUPADO</span>
    await tx.quarto.update({
      where: { id: dto.quartoId },
      data: { status: <span class="cs">'OCUPADO'</span> }
    });

    <span class="cm">// Se qualquer passo falhar → ROLLBACK automático</span>
    return reserva;
  });
}</div>
        </div>
        <div class="adr-subsection">
          <div class="adr-subsection-title">Mapa de Transações do Sistema</div>
          <table class="rules-table">
            <thead><tr><th>Operação</th><th>Entidades</th><th>Transação</th><th>Requisito</th></tr></thead>
            <tbody>
              <tr><td>Criar Reserva</td><td>Reserva + Quarto</td><td>✅ Crítica</td><td>RF12, RF15</td></tr>
              <tr><td>Cancelar Reserva</td><td>Reserva + Quarto</td><td>✅ Crítica</td><td>RF16, RF17</td></tr>
              <tr><td>Editar Reserva (trocar quarto)</td><td>Reserva + Quartos (2)</td><td>✅ Crítica</td><td>RF14</td></tr>
              <tr><td>Cadastrar Quarto</td><td>Quarto + QuartoCama</td><td>✅ Importante</td><td>RF01, RF02</td></tr>
              <tr><td>Cadastrar Hóspede</td><td>Hospede</td><td>❌ Não necessária</td><td>RF07</td></tr>
              <tr><td>Alterar Status do Quarto</td><td>Quarto (somente)</td><td>❌ Operação única</td><td>RF05</td></tr>
            </tbody>
          </table>
        </div>
        <div class="adr-subsection">
          <div class="adr-subsection-title">Consequências</div>
          <div class="cg">
            <div class="cbox pos"><div class="cbt">✅ Positivas</div><ul>
              <li>Atomicidade garantida: tudo ou nada nas operações críticas</li>
              <li>Elimina estados inconsistentes entre entidades relacionadas</li>
              <li>Rollback automático em caso de falha técnica ou de negócio</li>
              <li>Suporte nativo no Prisma via $transaction API</li>
              <li>Consistência garantida mesmo em cenários de concorrência</li>
            </ul></div>
            <div class="cbox neg"><div class="cbt">⚠️ Trade-offs</div><ul>
              <li>Transações longas podem gerar locks no banco de dados</li>
              <li>Ligeiro overhead de performance vs operações simples</li>
              <li>Necessidade de tratar exceções específicas de transação</li>
            </ul></div>
          </div>
        </div>
        <div class="adr-subsection">
          <div class="adr-subsection-title">Rastreabilidade</div>
          <p>Atende: <strong>RNF11</strong> (integridade em falhas), <strong>RF15</strong> (status automático ao criar), <strong>RF17</strong> (status automático ao cancelar), <strong>RF14</strong> (consistência ao editar reserva).</p>
