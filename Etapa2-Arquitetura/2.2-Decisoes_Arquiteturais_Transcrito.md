### 2. ADR-001 — Estilo Arquitetural: Monolito Modular

**Adoção de Monolito Modular em Camadas como estilo arquitetural principal**

* **Status:** ✅ Aceito
* **Prioridade:** 🔴 Crítica

#### Contexto
O sistema possui módulos inter-relacionados onde transações cruzadas são frequentes. Ao criar uma reserva, é necessário verificar e atualizar o status do quarto atomicamente. A equipe é pequena e o time-to-market é relevante. O escopo é limitado a um único hotel.

#### Alternativas Consideradas
| Opção | Vantagens | Desvantagens | Adequação |
| :--- | :--- | :--- | :--- |
| **✅ Monolito Modular** | ACID nativo, simplicidade, baixo custo, deploy único, chamadas em memória | Escala como unidade única; disciplina para evitar acoplamento | Alta — contexto limitado |
| **Microserviços** | Escala independente, resiliência por serviço | Alta complexidade, transações distribuídas, custo elevado, over-engineering | Baixa — complexidade desnecessária |
| **Monolito Simples** | Desenvolvimento ultra-rápido | Alto acoplamento, sem separação de responsabilidades | Baixa — inviável a longo prazo |

#### Decisão
Adotar **Monolito Modular em 4 Camadas**: Apresentação → Aplicação (API) → Serviços/Domínio → Persistência, com módulos independentes por contexto de negócio (Quartos, Hóspedes, Reservas) dentro de um único processo deployável.

#### Estrutura de Módulos
```text
// Organização modular interna do monolito
src/
├── modules/
│   ├── quartos/          // Bounded Context: Quartos
│   │   ├── controllers/
│   │   ├── services/
│   │   ├── repositories/
│   │   ├── entities/
│   │   └── dtos/
│   ├── hospedes/         // Bounded Context: Hóspedes
│   └── reservas/         // Bounded Context: Reservas
├── shared/               // Código transversal
│   ├── database/
│   ├── middleware/
│   └── exceptions/
└── config/
```

#### Consequências
**✅ Positivas:**
* Transações ACID nativas entre módulos
* Chamadas entre módulos em memória (sem latência)
* Deploy simplificado — um único artefato
* Debugging e rastreamento de erros facilitados
* Menor custo de infraestrutura
* Path claro de evolução para microserviços

**⚠️ Trade-offs:**
* Escala como unidade — módulos não escalam independentemente
* Falha afeta todo o sistema simultaneamente
* Necessidade de disciplina para evitar acoplamento indevido
* Qualquer alteração requer reimplantação completa

#### Rastreabilidade
Atende: **RNF11** (integridade de dados), **RNF13** (clean code), **RNF14** (modularidade), **RF15** (status automático ao criar reserva), **RF17** (status automático ao cancelar reserva).

### 4. ADR-003 — Banco de Dados: PostgreSQL

**Adoção de PostgreSQL como sistema gerenciador de banco de dados**

* **Status:** ✅ Aceito
* **Prioridade:** 🔴 Crítica

#### Contexto
Os dados do sistema são fortemente relacionais: um quarto tem múltiplas camas, uma reserva referencia quarto e hóspede, e o status do quarto deve ser consistente com as reservas ativas. Integridade referencial e suporte a transações ACID são requisitos não negociáveis.

#### Alternativas Consideradas
| SGBD | Tipo | Pontos Positivos | Pontos Negativos |
| :--- | :--- | :--- | :--- |
| **✅ PostgreSQL 15+** | Relacional | ACID, FK, constraints, JSON, open-source, gratuito | Overhead de configuração inicial |
| **MySQL 8** | Relacional | Popular, rápido para leituras simples | Menor conformidade SQL padrão, licença dual |
| **MongoDB** | NoSQL (Documento) | Flexibilidade de schema | Sem ACID cross-document, inadequado para dados relacionais |
| **SQLite** | Relacional embarcado | Zero configuração | Inadequado para produção multi-usuário, sem concorrência real |

#### Esquema Principal (Prisma SDL)
```typescript
model Quarto {
  id             String        @id @default(uuid())
  numero         String        @unique          // RF06
  capacidade     Int
  tipo           TipoQuarto                     // Básico | Moderno | Luxo
  precoDiaria    Decimal       @db.Decimal(10,2)
  frigobar       Boolean       @default(false)
  cafeManha      Boolean       @default(false)
  arCondicionado Boolean       @default(false)
  tv             Boolean       @default(false)
  status         StatusQuarto  @default(LIVRE)  // RF05
  camas          QuartoCama[]
  reservas       Reserva[]
  criadoEm       DateTime      @default(now())
  atualizadoEm   DateTime      @updatedAt
}

model Hospede {
  id        String    @id @default(uuid())
  nome      String
  sobrenome String
  cpf       String    @unique                // RF11
  email     String
  reservas  Reserva[]
  criadoEm  DateTime  @default(now())
}

model Reserva {
  id          String        @id @default(uuid())
  quartoId    String
  hospedeId   String
  quarto      Quarto        @relation(fields:[quartoId], references:[id])
  hospede     Hospede       @relation(fields:[hospedeId], references:[id])
  status      StatusReserva @default(ATIVA)
  criadoEm    DateTime      @default(now())
  canceladoEm DateTime?
}
```

#### Consequências
**✅ Positivas:**
* Integridade referencial garantida por Foreign Keys
* Transações ACID para operações críticas
* Constraints de unicidade (numero, CPF)
* Suporte nativo a JSON para dados futuros
* Gratuito, open-source, comunidade ativa

**⚠️ Trade-offs:**
* Necessita servidor dedicado (não embarcado)
* Schema rígido — alterações exigem migrations
* Maior consumo de recursos que SQLite

#### Rastreabilidade
Atende: **RNF11** (integridade de dados), **RF06** (número único de quarto), **RF11** (CPF único), **RF15** e **RF17** (consistência via transação).

### 6. ADR-005 — Repository Pattern

* **Status:** ✅ Aceito
* **Prioridade:** 🟠 Alta

#### Contexto
A camada de serviços não deve conhecer detalhes de implementação da persistência. O desacoplamento permite trocar o ORM ou banco sem impactar a lógica de negócio e viabiliza testes unitários via mock dos repositórios.

#### Implementação

  updateStatus(id: string, status: StatusQuarto): Promise<Quarto>;

// Implementação concreta com Prisma
class PrismaQuartosRepository implements IQuartosRepository {
  constructor(private prisma: PrismaClient) {}
  async findAll(filters?: QuartoFilters) {
    return this.prisma.quarto.findMany({ where: filters });
  }

class QuartosService {

### 8. ADR-007 — Transações ACID

**Uso de transações ACID para operações que afetam múltiplas entidades simultaneamente**

* **Status:** ✅ Aceito
* **Prioridade:** 🔴 Crítica

#### Contexto
Operações como "criar reserva" e "cancelar reserva" envolvem alterações em múltiplas tabelas. Se parte da operação falhar, o sistema pode ficar em estado inconsistente (reserva criada sem status atualizado, ou quarto liberado sem reserva cancelada). Transações ACID eliminam esse risco.

#### Implementação de Transação Crítica
```typescript
// Criar reserva — transação atômica (Prisma $transaction)
async criarReserva(dto: CreateReservaDto): Promise<Reserva> {
  return await this.prisma.$transaction(async (tx) => {

    // 1. Verificar disponibilidade dentro da transação (evita race condition)
    const quarto = await tx.quarto.findUnique({ where: { id: dto.quartoId } });
    if (quarto?.status !== 'LIVRE') {
      throw new ConflictException('Quarto indisponível');
    }

    // 2. Criar a reserva
    const reserva = await tx.reserva.create({ data: dto });

    // 3. Atualizar status do quarto para OCUPADO
    await tx.quarto.update({
      where: { id: dto.quartoId },
      data: { status: 'OCUPADO' }
    });

    // Se qualquer passo falhar → ROLLBACK automático
    return reserva;
  });
}
```

#### Mapa de Transações do Sistema
| Operação | Entidades | Transação | Requisito |
| :--- | :--- | :--- | :--- |
| Criar Reserva | Reserva + Quarto | ✅ Crítica | RF12, RF15 |
| Cancelar Reserva | Reserva + Quarto | ✅ Crítica | RF16, RF17 |
| Editar Reserva (trocar quarto) | Reserva + Quartos (2) | ✅ Crítica | RF14 |
| Cadastrar Quarto | Quarto + QuartoCama | ✅ Importante | RF01, RF02 |
| Cadastrar Hóspede | Hospede | ❌ Não necessária | RF07 |
| Alterar Status do Quarto | Quarto (somente) | ❌ Operação única | RF05 |

#### Consequências
**✅ Positivas:**
* Atomicidade garantida: tudo ou nada nas operações críticas
* Elimina estados inconsistentes entre entidades relacionadas
* Rollback automático em caso de falha técnica ou de negócio
* Suporte nativo no Prisma via `$transaction` API
* Consistência garantida mesmo em cenários de concorrência

**⚠️ Trade-offs:**
* Transações longas podem gerar locks no banco de dados
* Ligeiro overhead de performance vs operações simples
* Necessidade de tratar exceções específicas de transação

#### Rastreabilidade
Atende: **RNF11** (integridade em falhas), **RF15** (status automático ao criar), **RF17** (status automático ao cancelar), **RF14** (consistência ao editar reserva).
