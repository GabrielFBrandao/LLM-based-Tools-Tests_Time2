## 3. Justificativa da Escolha: Monolito Modular

### 3.1 Contexto da Decisão

**Características do Sistema**:
- Sistema para **um único hotel**
- Escopo bem definido e limitado
- 3 módulos principais inter-relacionados
- Equipe provavelmente pequena
- Necessidade de desenvolvimento ágil
- Baixa complexidade de negócio inicial

---

### 3.2 Por Que NÃO Microserviços?

#### **Desvantagens para este Contexto**:

❌ **Complexidade Desnecessária**:
- Overhead de comunicação entre serviços
- Necessidade de API Gateway, Service Discovery, Circuit Breakers
- Gerenciamento de múltiplos deployments

❌ **Consistência de Dados**:
- Transações distribuídas (Saga Pattern) para operações como criar reserva
- Eventual consistency pode ser problemática para reservas (race conditions)

❌ **Overhead Operacional**:
- Necessidade de containerização (Docker/Kubernetes)
- Monitoramento distribuído
- Logs agregados
- Custo de infraestrutura maior

❌ **Time-to-Market**:
- Desenvolvimento inicial mais lento
- Maior complexidade de testes

**Exemplo de Problema**:

Cenário: Criar Reserva em Microserviços
1. ReservasService chama QuartosService (HTTP)
2. Verifica disponibilidade
3. QuartosService atualiza status
4. Se falhar, precisa compensar (rollback distribuído)
5. ReservasService cria reserva
6. Se falhar, precisa reverter status do quarto

Vs. Monolito:
1. Transaction begin
2. Verifica disponibilidade
3. Atualiza status
4. Cria reserva
5. Commit (tudo ou nada - ACID)

---

### 3.3 Por Que Monolito Modular?

#### **Vantagens**:

✅ **Simplicidade**:
- Um único processo
- Um único deployment
- Transações ACID nativas
- Debugging mais fácil

✅ **Desempenho**:
- Chamadas locais (memória) vs chamadas HTTP
- Sem latência de rede entre módulos
- Joins eficientes no banco de dados
- Cache compartilhado

✅ **Consistência**:
- Transações ACID garantidas
- Integridade referencial do banco
- Sem eventual consistency

✅ **Desenvolvimento Ágil**:
- Menor overhead de setup
- Testes mais simples
- Refatoração mais fácil
- Time-to-market reduzido

✅ **Custo de Infraestrutura**:
- Um único servidor/container
- Menor consumo de recursos
- Escalabilidade vertical suficiente

✅ **Modularidade**:
- Módulos bem definidos (Quartos, Hóspedes, Reservas)
- Baixo acoplamento entre módulos
- Alta coesão dentro de cada módulo
- **Evolução futura facilitada** para microserviços se necessário

---

### 3.4 Análise de Desempenho

#### **Estimativa de Carga para Um Hotel**:

Premissas:
- Hotel médio: 50-100 quartos
- Taxa de ocupação: 70%
- Check-ins/dia: ~30
- Reservas/dia: ~50
- Consultas/dia: ~200

Total de operações/dia: ~280
Pico (horário comercial 8h): ~35 operações/hora

**Capacidade do Monolito**:
- Servidor modesto (2 vCPU, 4GB RAM): **1000+ req/s**
- Nossa carga: **~0.01 req/s** (35 op/hora)
- **Margem de segurança**: 100.000x

**Conclusão**: Monolito é mais que suficiente. Microserviços seriam over-engineering.

---

### 3.5 Análise de Escalabilidade

#### **Escalabilidade Vertical** (Suficiente)

Cenário 1: Hotel cresce de 50 para 200 quartos
- Carga 4x maior
- Ainda ~0.04 req/s
- Servidor atual ainda suporta

Cenário 2: Rede de 10 hotéis
- Carga 10x maior
- ~0.1 req/s
- Servidor atual ainda suporta
- Alternativa: Multi-tenant no mesmo monolito


#### **Escalabilidade Horizontal** (Se necessário)

Se futuramente precisar escalar horizontalmente:
1. Load Balancer (Nginx/HAProxy)
2. Múltiplas instâncias do monolito
3. Sessões stateless (JWT)
4. Cache compartilhado (Redis)

Essa arquitetura permite isso sem refatoração!

#### **Path de Evolução**

```
Fase 1: Monolito Modular (Atual)
         ↓
Fase 2: Monolito + Cache + Load Balancer (Se necessário)
         ↓
Fase 3: Extração de serviços críticos (Se REALMENTE necessário)
         - Serviço de Reservas independente
         - Serviço de Pagamentos (novo)
         - Monolito continua com Quartos e Hóspedes
```

**Benefícios**:
- ✅ Cada módulo é independente
- ✅ Fácil localizar código relacionado
- ✅ Testes isolados por módulo
- ✅ Onboarding de novos desenvolvedores facilitado
- ✅ Preparado para extração futura se necessário

#### **Princípios Aplicados**:

1. **Separation of Concerns**: Cada camada tem responsabilidade única
2. **Dependency Inversion**: Camadas superiores não conhecem implementação das inferiores
3. **Single Responsibility**: Cada módulo gerencia um contexto de negócio
4. **Open/Closed**: Fácil adicionar novos módulos sem modificar existentes

### 3.7 Comparação: Monolito vs Microserviços

| Critério | Monolito Modular | Microserviços | Vencedor |
|----------|------------------|---------------|----------|
| **Complexidade Inicial** | Baixa | Alta | ✅ Monolito |
| **Time-to-Market** | Rápido (2-3 meses) | Lento (4-6 meses) | ✅ Monolito |
| **Consistência de Dados** | ACID nativo | Eventual consistency | ✅ Monolito |
| **Desempenho** | Excelente (memória) | Bom (rede) | ✅ Monolito |
| **Debugging** | Simples | Complexo (distribuído) | ✅ Monolito |
| **Escalabilidade** | Vertical + Horizontal | Horizontal independente | ⚖️ Empate* |
| **Custo Infraestrutura** | Baixo | Alto | ✅ Monolito |
| **Deploy** | Um único deploy | Múltiplos deploys | ⚖️ Depende** |
| **Resiliência** | Falha afeta tudo | Falha isolada | ❌ Microserviços |
| **Tecnologia** | Stack único | Polyglot possível | ❌ Microserviços |

*Para este contexto, escalabilidade vertical é suficiente
**Deploy único é vantagem neste contexto (menor overhead)

### 3.8 Riscos e Mitigações

#### **Risco 1: Acoplamento Excessivo**
**Mitigação**:
- Interfaces bem definidas entre módulos
- Dependency Injection
- Comunicação via eventos internos (Event Bus local)

#### **Risco 2: Banco de Dados como Ponto Único de Falha**
**Mitigação**:
- Backup automatizado diário
- Réplicas read-only (se necessário)
- Monitoramento de saúde

#### **Risco 3: Escalabilidade Futura**
**Mitigação**:
- Arquitetura modular permite extração de serviços
- Código já organizado por bounded contexts
- Migration path clara para microserviços

#### **Risco 4: Deploy Monolítico**
**Mitigação**:
- CI/CD automatizado
- Blue-Green deployment
- Feature flags para releases graduais
- Rollback rápido
