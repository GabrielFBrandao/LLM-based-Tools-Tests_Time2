# Input:

> "Agora, com base nos requisitos definidos anteriormente para o Sistema de Reserva de Hotel, realize o Projeto de Software.
> Primeiramente, vamos focar na arquitetura geral:
> 1. Proponha uma arquitetura para este sistema (ex.: camadas, microserviços, ou monolito modular).
> 2. Justifique a escolha considerando desempenho, escalabilidade e manutenção."

---

# Output:

# Etapa 2 — Arquitetura Proposta

## 1. Visão Geral
Propõe-se um Monólito Modular em camadas, com fronteiras bem definidas (Clean/Hexagonal-like), visando simplicidade inicial, baixo custo operacional e caminho de evolução para serviços. A aplicação é dividida em:
- Camada de Apresentação (Web UI)
- Camada de Aplicação (Casos de Uso/Orquestração)
- Camada de Domínio (Entidades, VOs, Regras de Negócio)
- Camada de Infraestrutura (Persistência, Autenticação, Logging, Mensageria opcional)

Tecnologias de referência (sugestão):
- Backend: Node.js (NestJS) ou Java (Spring Boot) com arquitetura hexagonal.
- Frontend: SPA com React ou Angular; componentes modernos (Material UI/Angular Material) com paleta verde/azul.
- Banco: Relacional (PostgreSQL) inicialmente; opção NoSQL para logs/observabilidade.
- Autenticação/Autorização: JWT + RBAC (Admin, Atendente, Manutenção).
- Observabilidade: Logs estruturados (JSON), métricas (Prometheus), tracing opcional.


## 2. Módulos Funcionais (Bounded Contexts internos)
- Quartos: cadastro, edição, comodidades, disponibilidade, camas, listagem e filtros.
- Hóspedes: cadastro, listagem, busca.
- Reservas: criação/edição, visualização de ocupação (chips), regras de disponibilidade.
- Identidade & Acesso: usuários, perfis (RBAC), autenticação.
- Suporte/Comum: exportação CSV, auditoria/logs, notificações (futuro), i18n.

Cada módulo expõe portas de aplicação (use cases) e depende de portas de infraestrutura (repos, serviços externos), mantendo baixo acoplamento.


## 3. Camadas e Responsabilidades
- Apresentação (UI/API):
  - Frontend SPA comunicando via REST/GraphQL.
  - Backend expõe controladores/handlers (adapta protocolo → comandos/queries da aplicação).
  - Validações de borda (DTOs, schema validation), mensagens claras (RF-17), acessibilidade (RNF-01).

- Aplicação:
  - Orquestra casos de uso: CadastrarQuarto, AtualizarDisponibilidade, CriarReserva, etc.
  - Regras de orquestração e políticas de transação (RNF-04).
  - Não contém lógica de domínio complexa; coordena entidades/serviços de domínio.

- Domínio:
  - Entidades: Quarto, Hospede, Reserva, Usuario, Perfil.
  - VOs: CPF, Email, NumeroQuarto, PrecoDiaria, Disponibilidade, TipoQuarto, TipoCama.
  - Serviços de domínio: PoliticaDisponibilidade, ServicoReserva (invariantes).
  - Eventos de domínio internos para auditoria/integrações futuras.

- Infraestrutura:
  - Repositórios (ORM: TypeORM/JPA) para PostgreSQL.
  - Autenticação/autorização (JWT, RBAC), criptografia de senhas (RNF-03).
  - Logging e métricas (RNF-07), exportação CSV, mensageria futura (ex.: para e-mails/integrações).


## 4. Modelo de Dados (alto nível)
- Quarto(id, numero UNIQUE, capacidade, tipo, preco_diaria, comodidades: frigobar|cafe|ar|tv, disponibilidade, ativo)
- Camas(id, quarto_id FK, tipo_cama)
- Hospede(id, nome, sobrenome, cpf UNIQUE, email, ativo)
- Reserva(id, quarto_id FK, hospede_id FK, status, criado_em, atualizado_em) — escopo atual sem datas; estado controla ocupação.
- Usuario(id, login, senha_hash, perfil)
- Auditoria(id, entidade, entidade_id, acao, usuario, timestamp, payload)

Índices em numero (Quarto), cpf (Hospede) e chaves estrangeiras. Tabelas com colunas ativo para soft delete (RF-16).


## 5. Integração e Comunicação
- Frontend ↔ Backend: REST (JSON). Endpoints versionados: /api/v1/...
- Backend ↔ DB: ORM; transações envolvendo Reserva e Quarto.
- Observabilidade: logs estruturados por correlação de requestId.


## 6. Implantação e Infraestrutura
- Deploy inicial: contêiner único (monólito) + banco gerenciado (PostgreSQL). Docker Compose para dev.
- Escalabilidade horizontal: escalar instâncias do monólito (stateless) por trás de um load balancer; sessões com JWT.
- Migrações de banco com ferramenta (TypeORM migrations/Flyway).


## 7. Segurança
- Validações server-side (CPF, e-mail, unicidade) e client-side (ux).
- Proteções XSS/CSRF/SQL Injection (RNF-03).
- RBAC aplicado nos controladores de aplicação (RF-20).
- Logs de segurança e auditoria (RNF-07, RF-15).


## 8. Justificativa da Escolha
- Desempenho:
  - Monólito modular reduz a latência de chamadas internas vs microserviços.
  - Transações simples e locais garantem consistência (RNF-04) e bom throughput para até 100 usuários simultâneos (RNF-09).
  - Frontend SPA com filtros client-side quando possível e paginação/queries eficientes (índices) suportam RNF-02.

- Escalabilidade:
  - Escala horizontal do monólito é suficiente para a meta (RNF-09). Componentes stateless e cache HTTP auxiliam.
  - Possibilidade de extração futura de contextos (ex.: Reservas) para um serviço independente caso a demanda cresça (estratégia Strangler Fig).

- Manutenção:
  - Camadas claras e portas/adapters (hexagonal) minimizam acoplamento e favorecem testes (RNF-06).
  - Bounded contexts internos organizam a base por domínio, facilitando evolução e ownership.
  - Padrões consistentes (DTOs, casos de uso, repositórios, eventos) permitem onboarding rápido e maior qualidade.

Conclusão: Monólito Modular em camadas com princípios hexagonais atende ao escopo atual com ótima relação custo-benefício, cobre RNFs críticos (desempenho, segurança, manutenibilidade) e mantém rota de evolução para uma arquitetura distribuída se necessário.
